## 4. 已完成任务：序列对搜索 + LP 定位（结果见原型 README 第 9 节）

### 4.1 目标

在同一合成算例、同样的评分定义（v2）下，**比 `placement_fast.py` 更快地得到更好的 J**。对比口径：3 个以上种子，记录 5 / 10 / 20 / 60 秒时的 J 中位数。

### 4.2 方法

**表示：** 解 = (Γ⁺, Γ⁻, 每块姿态, 每个复制组的内部排法)。

- 序列对规则：i 在 j 左边 ⇔ 两个序列中 i 都在 j 前；i 在 j 下方 ⇔ Γ⁺ 中 i 在 j 后、Γ⁻ 中 i 在 j 前。
- 已知定理：任意无重叠布局压紧后都能由某个序列对表示，所以不会因为换表示而丢掉最优解（摆放部分）。

**评估一个候选（内层，精确）：**

1. 由序列对和姿态得到差分约束：x_j − x_i ≥ w_i + δ 等。
2. max-plus / 最长路得到该骨架下的最小 W*、H*（已有实现：`解析摆放示例.py`、`对比实验/benchmark.py` 中的 `sp_pack`）。
3. LP：在 W ≤ W*、H ≤ H*（可再试几个放宽比例）下最小化管长下界。
   - 两端点管网：姿态对决定弯头下界 c；c > 0 时用伸出点下界（线性 + 绝对值）；c = 0 时 LP 先用曼哈顿距离，再由校验器判断能否直连。
   - 多端点管网：伸出点坐标跨度（max − min，线性化）。
   - 可先用 SciPy HiGHS，n ≈ 12 时每次约毫秒级（需实测）；差分约束 + 绝对值的 LP 是最小费用流的对偶，之后可换成网络单纯形或 Rust 实现提速。
4. 用 `placement_cpsat.validate(..., lb="v2")` 计算最终 J，**所有方法以校验器为准**。

**外层搜索：**

- 模拟退火或禁忌搜索。邻域：交换 Γ⁺ 中两块；交换 Γ⁻ 中两块；两个序列同时交换；改一个块的旋转；改复制组的内部排法。
- 12 核并行：多进程、不同种子，定期同步当前最好解。
- 初始解：由 `placement_fast.py` 的 1 秒解推导序列对（按相对位置关系排序，检查一致性），失败则随机。

### 4.3 需要处理的细节（已知坑）

1. **固定块**（建筑立管固定在 (0,0)）：LP 中加 x = 固定值；若序列对使其不可行，LP 报不可行，该候选直接拒绝。
2. **检修区**：检修区与其他块不重叠，这不由序列对自动保证。两种处理方式：
   - (a) 在 LP 中按“检修区在块的哪一侧”追加差分约束，与序列对关系一致时加入，冲突时拒绝；
   - (b) 校验器发现冲突时给候选加罚。
   先用 (b) 快速验证，再决定是否改 (a)，并在结果中注明。
3. **`service_zones_inside_footprint`** 为 `true` 时，检修区也要进入 W、H 的计算。
4. **长宽比 κ**：按 `room_of` 补足，与现有评分一致。
5. **复制组**：组内所有块共用同一内部排法；旋转各自独立（原型 README 第 6 节第 5 条）。
6. **面积与管长的权衡**：只在 W*、H* 下优化管长，可能错过“面积稍大、管长明显更短”的解。需在几个放宽比例（例如 1.00、1.05、1.10）上分别求解，取 J 最小者。

## 8. 求解思路讨论（2026-09-17，未定案）

用户要求：
- 方案要通用，不假定设备位置或布置模式（例如管廊）；
- 给端口留空余是可以的；
- 随便给一组设备组合，都应能排出好的方案；
- 不能出现“设备定死后管道排不下、陷入无限求解”。

提出过的方案：先构造一个保证可行的松散方案，再联合压缩改进。

用户质疑：初始解可能很差，压缩改进很难达到好方案。

改为：搜索相对结构（序列对、朝向、管道走哪条缝隙），给定结构后用线性规划一次求最紧凑尺寸（不是逐步压缩），最后再做精确布管。

**小实验（布管原型 README 第 5 节）：** 只实现了“按侧出管留空”这一半。
- 3 个种子都布通 25/25，但各剩 1 对冲突；对照方法每次有 2–3 个管网布不通。
- 剩余冲突来自高设备之间的窄缝：只计了端口出管，没计管道穿过缝隙的需求。
- 管长比下界多 50%–75%。

**续做“缝隙穿行容量”（布管原型 README 第 6 节）：** 3 个种子都布通，但各剩 2–3 对冲突，比只做出管留空还略差；评估速度降为约 1/7。

**已定下一步：** 做粗网格快速布管（秒级），先用于快速判断摆放能否布通，再放进摆放搜索，用真实冲突数代替人为估计公式；精细布管只对最终方案做一次。

**粗网格快速布管已完成（布管原型 README 第 7 节）：**
- 0.3 m 格子，每个摆放约 1 秒；在 9 个已有摆放上，“能否布下”的判断与精细布管一致。
- 粗网格判 B、C 可布，但精细布管各剩 1–3 对冲突。原因是规则差异还是精细协商不足，尚未区分。

**走廊引导（布管原型 README 第 8 节）：已中止，结果更差。**
- 粗网格路径外扩 1 格作走廊，精细 A* 走出走廊加价 ×3。B 种子 0 第 16 轮冲突边 329（不引导为 25），每轮慢 3–10 倍。
- 原因：软加价削弱 A* 启发式，搜索爆炸、触到扩展上限。剩余冲突的成因仍未区分。

**阶段反思（2026-09-17）：**
1. 多次在查清根因前先调性能或调度；应先定位冲突卡在哪。
2. “设计估计公式 → 跑全流程（40 分钟以上）”的迭代太慢；应先有秒级可靠的评估工具（粗网格已具备）。
3. 往精细 A* 里加软代价（拥堵、走廊）都会让搜索爆炸；分层应当用硬约束或直接检查。
4. 算例、设备库、布管参数都是自拟，结论受数值影响，需用户确认真实数据。
5. 仍是“先摆放、后布管”；要满足用户要求，布管可行性需进入摆放搜索本身。

**已定下一步（用户已同意）：**
1. 冲突点单独检查：固定其他管道为硬障碍，只对冲突管网重搜，判断是“协商不足”还是“空间不够”；前者可直接作为布管最后的清理步骤。
2. 结果出来后再设计：把粗网格布管（约 1 s）放进摆放搜索，精细布管只对最终方案做一次。
