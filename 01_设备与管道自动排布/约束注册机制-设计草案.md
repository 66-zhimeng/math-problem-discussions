# 约束注册机制：设计草案

日期：2026-09-16。状态：讨论草案，**未实现**，接口名称均为示意。

目标：计算内核中的规则可以用配置文件或一次函数调用注册，并能跨项目复用；求解算法尚未选定，本设计不依赖具体算法。

对应数学文档：第 5 节（规则模式与违反度）、第 11.2 节（S(X) 与用户规则分离）。

---

## 1. 两类约束分开对待

| 类别 | 例子 | 能否注册、关闭或软化 |
|---|---|---|
| **模型语义 S(X)** | 连接拓扑一致、端口对接、模块刚性复制、直管沿 U₆、对象间必须接直管 | 不能。由内核固定实现，不对外开放关闭。 |
| **用户规则** | 对齐、净距、禁止叠放、每根管高度变化次数上限、区域限制 | 能。通过注册机制添加，模式为 off / hard / soft。 |

这样可以避免第 11.9 节的问题：配置错误不会让内核悄悄丢掉基本语义。

项目差异较大、但属于几何语义的内容（如“是否允许叠放”）放在用户规则一侧，由各项目配置决定。

## 2. 三层结构

### 2.1 规则模板：写一次，所有项目复用

模板描述“一种数学关系”，不绑定具体对象。它是一个函数，输入当前布局和作用对象，输出**残差**：

- 不等式模板：返回 g，要求 g ≤ 0。
- 等式模板：返回 h，要求 h = 0。
- 返回值使用真实单位，例如 mm、次数。

```python
from layout_kernel import rule_template

@rule_template(name="max_height_changes", kind="ineq",
               params={"K": int}, unit="次")
def max_height_changes(layout, targets, K):
    # 每条外部连接一个残差：高度变化次数 − K ≤ 0
    return [layout.height_changes(e) - K for e in targets]
```

这里的 `layout.height_changes(e)` 是内核提供的几何查询。模板只做组合，不自己重算几何，这样满足第 11.2 节“所有规则都从同一个 Φ(X) 计算”。

### 2.2 规则实例：模板 + 作用对象 + 参数 + 模式

在具体项目中使用模板，有两种等价写法。

**配置文件（JSON，独立文件）：**

```json
{
  "schema_version": "0.1",
  "rules": [
    {
      "id": "高度变化上限",
      "description": "每条外部连接最多改变高度 2 次",
      "template": "max_height_changes",
      "targets": { "kind": "connection" },
      "params": { "K": 2 },
      "mode": "hard"
    },
    {
      "id": "水泵XZ对齐",
      "description": "带 pump 标签的设备在世界坐标 X、Z 上对齐",
      "template": "align_axes",
      "targets": { "tag": "pump" },
      "params": { "axes": ["x", "z"], "frame": "world", "feature": "origin" },
      "mode": "soft",
      "weight": 1.0,
      "scale": 50,
      "aggregate": "mean",
      "tol": 1
    }
  ]
}
```

**函数调用：**

```python
model.add_rule("高度变化上限", template="max_height_changes",
               targets=select.connections(), params={"K": 2}, mode="hard")
```

**临时规则：** 不值得做成模板时，直接传函数。

```python
model.add_rule("冷机离东墙至少2m", kind="ineq", mode="hard",
               targets=select.by_id("CH-1"),
               fn=lambda layout, t: [2000 - layout.distance(t[0], "东墙")])
```

### 2.3 对象选择器

规则通过选择器找到作用对象，只能依据 JSON 中确实存在的信息：

- `id`：按对象编号。
- `kind`：设备、管件、连接、模块实例。
- `tag` / 属性：JSON 中已有的字段。
- 组合：并、交、差。

总管的教训：若 JSON 中没有某种标记，就无法可靠选中对应对象，规则也无从定义。选择结果为空时，内核应报告警告，而不是静默通过。

## 3. 内核如何统一处理一条规则

对任意规则 r，内核只依赖残差，处理方式与数学文档第 5 节一致：

1. 计算残差向量。
2. 逐项违反度：不等式 `max(0, g − tol)`，等式 `max(0, |h| − tol)`。
3. 按 `aggregate` 聚合：mean、max 或 sum。
4. 按模式处理：
   - `off`：不计算。
   - `hard`：聚合后的违反度必须为 0，否则该布局不可行。
   - `soft`：`weight × 违反度 / scale` 加入目标函数。
5. 输出报告：每条规则的模式、残差、违反度和是否满足。

---

## 4. 求解器需要的额外信息（可选能力）

只提供残差函数，任何算法都能**检查**一个完整布局是否合法，但不一定能高效**搜索**。模板可以选择性声明以下能力；没有声明时，内核退回“生成完整候选后再检查”。

| 能力 | 作用 | 例子 |
|---|---|---|
| `partial`：部分布局上的下界 | 管路搜索到一半就能剪枝 | 高度变化次数只增不减，已超过 K 可立即放弃 |
| `linear_form`：线性表达 | 供整数规划等方法直接编码 | `x_i − x_j = 0` 这类对齐 |
| `bounds`：变量范围收缩 | 预处理缩小搜索空间 | 区域限制直接变成坐标上下界 |
| `depends_on`：依赖的变量 | 判断能否分块求解，见数学文档第 8 节 | 对齐规则只依赖两台设备的位姿 |

这些是加速信息。它们必须与残差函数含义一致；不一致时以残差为准，内核可以抽样校验。

## 5. 注册与加载时的检查

对应第 11.9 节：

1. 模板名是否存在，参数类型与单位是否正确。
2. 选择器是否为空。
3. 同一 id 或完全相同的规则是否重复注册。重复不叠加罚分。
4. 明显矛盾的硬规则，例如同一对象被锁在两个位置，加载阶段即报告。
5. 求解结束时区分：满足全部硬规则、未找到可行解（超时）、已证明无解。

## 6. 使用流程：AI 编写配置，人用自然语言确认

用户确认（2026-09-16）：规则配置为**独立 JSON 文件**，主要由 AI 编写和调用；人不直接编辑配置，只用自然语言确认。

    人：描述项目需求
     ↓
    AI：读取模板目录，列出要考虑的对象、约束、参数和未定项，用自然语言提问
     ↓
    人：自然语言回答
     ↓
    AI：生成拓扑 JSON 与规则 JSON → 内核校验 → 求解
     ↓
    AI：把内核的结构化报告翻译成自然语言，说明满足了什么、违反了什么、哪些参数需要再确认

为适配这一流程，内核需要：

1. **模板目录可导出。** 内核输出所有已注册模板的机器可读说明：名称、自然语言含义、参数名、类型、单位、是否必填、适用对象类型。AI 据此提问和编写配置，不凭记忆猜模板。
2. **JSON Schema 校验。** 规则文件、拓扑文件都有 schema；AI 写错字段在加载时报错，并给出可定位的错误信息。
3. **项目参数不写死。** K、最小直管长度 ℓ_min 等均为配置参数，内核中没有隐含默认值；缺失时报错，由 AI 回头向人确认。ℓ_min 可以按管径或按连接分别给定。
4. **每条规则带 `description`。** 用自然语言写明含义，便于 AI 向人复述、人逐条确认。
5. **配置文件只引用已注册模板。** JSON 中不嵌入可执行代码。确实需要新的数学关系时，由 AI 在代码中新增模板并注册，之后配置文件再引用。
6. **报告为结构化 JSON。** 包含每条规则的残差、违反度、是否满足，以及求解状态（可行 / 超时未找到 / 已证无解），供 AI 转述。
